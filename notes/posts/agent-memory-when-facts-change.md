When a fact changes, an agent's memory has three jobs: answer with the new fact, notice that something changed, and tell me when my own question still assumes the old fact. On two months of my own work history, overwriting old facts failed the second job badly. It said "I don't know" 34 times, and in all 34 the new fact was sitting in the notes it was shown. Keeping old facts with a "no longer valid" label did best, but no design handled the third job (0% to 9%) until I added one sentence to the answer prompt, which took it from 3% to 91%.

This follows [my first five memory experiments](notes.html?post=ai-agent-memory-experiments) on [Saati, my personal agent](notes.html?post=building-a-personal-ai-agent). Same data, same small free model (Gemini 3.5 Flash-Lite), same rules: I wrote down the setup and my predictions before each run, cached every model call, and graded answers blind.

## Key takeaways

- Memory isn't one skill. Regrouping my first five runs by the abilities in the LongMemEval benchmark, every ability had a different winner.
- Overwriting a changed fact made the agent unable to notice the change: 34 "I don't know" answers with the new fact in front of it. Labelled old facts scored 59% against 33% (95% CI of the gap +14 to +37).
- Every design failed when my question assumed an outdated fact (0% to 9%). The cause was the answer prompt, not the memory. One sentence raised it to 91%.
- That sentence over-fired at first, calling 4 of 20 ordinary questions outdated. A tighter wording kept the gain with no false flags, and it held on 36 new questions (21% to 88%).
- In the live agent, strict project matching plus a confirmation step cut invented projects from 3 to 0 over 78 tries, at a small cost to creating real ones.

## The question

Part 1 ended with a clear rule: never overwrite a fact, keep the old one and mark when it stopped being true. Labelled facts scored 95% against 76% for overwriting. But all of Part 1's questions asked about the past or the present directly. Real conversations are messier than that. I often ask things like "since the repo is still private, what should the README say?", when the repo went public a week ago. A good assistant should catch that.

So this round asks a narrower question. When a fact changes, does the memory let the agent *notice* the change, and does it push back when my question is out of date?

Two 2026 papers shaped the tests. [STALE](https://arxiv.org/abs/2605.06527) (Chao et al.) checks whether a memory system catches outdated information in three ways, which I copied. And [LongMemEval](https://arxiv.org/abs/2410.10813) (Wu et al., ICLR 2025) splits memory into separate abilities, which gave me a better way to read my old results. The last run comes from a different problem, an annoying bug in Saati itself, and borrows its scoring from [τ-bench](https://arxiv.org/abs/2406.12045) (Yao et al., 2024).

## Setup

- **Data and memory:** the frozen memory stores from Part 1's first run, built from 23 of my coding sessions (about 2.1 million characters, July to November 2026). Three stores: **append** (keep every fact), **overwrite** (replace a fact when it changes, as in the 2025 Mem0 paper), and **labelled** (keep old facts, marked "no longer valid since <date>").
- **Answering:** keyword search (BM25) picks the 10 best notes, then `gemini-3.5-flash-lite` answers from them, with Part 1's prompt unless a run changes it.
- **Grading:** blind and shuffled; correct, partly correct (half a point), or wrong. In each run I mixed already-graded answers into the sheet as a consistency check, and they were re-graded the same way every time. A second, independent AI grader re-graded 30 answers from these runs and agreed on 26 (Cohen's kappa 0.78). All 4 disagreements were "partly" against "wrong"; I went through them and kept the original grades. Using the second grader's grades instead would move any score by 3 points at most.
- **Statistics:** paired bootstrap 95% confidence intervals (CI). If a CI includes zero, the difference could be chance.

## Memory is several skills, not one

Before running anything new, I took every grade from Part 1 and regrouped it by the abilities LongMemEval defines. This cost no model calls; it's the same grades, read a different way. The mapping was fixed before I scored anything: current-state questions count as knowledge updates, history and date questions as temporal reasoning, cross-project questions as reasoning across sessions, and stable and technical questions as extracting details.

That's 51 questions on each of the three stores, 153 answers in total. Before running anything, I checked that the labelled store's search actually surfaced the old, invalidated fact for all 17 premise questions, so the test really did put outdated memory in front of the model.

One honest caveat about this run: the changes in my data are explicit (I said "we moved to X"), while STALE's hard case is an implicit conflict the agent has to infer. So this is an easier version of their test, not a copy of it. Also, an AI assistant drafted the questions and screened them against the stores. While screening, it reworded 7 questions whose new fact the labelled store's search missed, and dropped none.

**Findings.** The interesting part is *how* each design failed. Append was the only one that confidently gave me outdated facts, 8 times, because it had both versions and no way to tell which was newer. Overwrite never gave an outdated answer, which sounds good until you see why. It said "I don't know" 34 times, and I checked every one: the new fact was among the notes in all 34. With the old fact gone and no label, the model couldn't tell that "tests run on all 6 universes" answers "are the tests still only planned?". Nothing in front of it said a change had happened.

And no design handled questions built on an old fact. They didn't agree with me, either. Across the three stores, 46 of 51 of those answers were "I don't know". The model refused instead of correcting me.

**What it means.** Part 1 said overwriting loses history. This run says something stronger: it loses the ability to *notice* change at all. Labels fix that. But the refusals pointed at the prompt rather than the memory. Part 1's answer prompt says "if the notes do not contain the answer, say I don't know", and a question with a false premise has no answer in that literal sense. So I tested the prompt next.

## Run 6b: one sentence

Same labelled store, same 51 questions. The only change was one sentence added to the answer prompt: check whether the question assumes something the notes show is no longer valid, and if it does, say so, give the current state, and then answer if possible.

I predicted the premise questions would rise by at least 20 points and the other two types would drop by no more than 10.

## Run 8: does the agent invent projects?

This one came from using Saati rather than from a paper. It kept creating projects that didn't exist. A folder name in a message would become a project. A passing mention of a tool would become a project. Once, it created one right after I said "don't add it". The cause was loose name matching plus creating projects automatically whenever it wasn't sure.

The fix on 15 November had three parts: strict name matching, aliases (so a folder name maps to the project it belongs to), and a two-step confirmation, where Saati asks and only creates the project after I say yes in a later message.

To measure it I borrowed τ-bench's **pass^k**: a conversation only counts if the agent handles it correctly on all k repeated tries. That's a fair test for an agent you rely on every day, because a fix that works two times out of three still leaves you cleaning up the database.

**Setup.** 26 scripted conversations of 7 types, 3 tries each, run against both the old code and the new code. Both started from the same database backup, loaded fresh into memory for every try. The model calls were real; Telegram was stubbed out; and the score came from rules applied to what changed in the database. An AI assistant wrote the scenarios.

## What I changed in Saati

1. Old facts stay, marked as replaced with a date. Nothing gets overwritten.
2. The answer prompt corrects outdated assumptions, but only when the question itself relies on one.
3. New projects need an explicit yes in a later message, and names match strictly or through aliases.

## Limits

This is a case study: one person's data, one small model, and 6 to 17 questions per group, so differences under about 15 to 20 points could be chance. Only the results whose confidence intervals exclude zero are firm. An AI assistant drafted and screened the Run 6 questions and wrote the Run 8 scenarios, and an AI grader graded everything. A second AI grader checked 30 answers, and I reviewed the disagreements. The changes in my data are explicit, which makes this easier than STALE's own test. Most of Run 7c's outdated-fact questions reuse Run 6's changes. Run 8's conversations are scripted, not real use, and each was tried only 3 times.

Next, I want to tackle the cross-project mix-up from Run 7c, and test memory poisoning: what happens when something false gets written into memory in the first place.

## Update, 19 November 2026: Run 9, the project mix-up

Run 7c left one error: asked which Python version my time-series dashboard uses, the agent gave my portfolio project's Python 3.12. The cause turned out to be simple. The stored note reads "The project uses Python 3.12 ..." with no project name, and 8 of my 259 stored notes start like that. The extraction step knew the project for every note; the stored text just didn't keep it.

I tested three versions on 22 new questions. In 11 "trap" questions, the only matching note belongs to a different project, so the right answer is "the notes don't cover this" (or naming the other project). The other 11 ask the same thing about the right project. The versions: notes as before, each note shown with `[project: name]`, and labels plus a rule to use only notes about the asked project.

| Traps (11) | 68% | 100% | 100% |
| Traps on unnamed notes (7) | 50% | 100% | 100% |
| Normal questions (11) | 91% | 100% | 100% |

Labels added 32 points on the traps (95% CI +9 to +59) and cost nothing on normal questions. Every trap the agent fell for was built on a note with no project name, and the extra rule added nothing beyond the label. Same limits as above: 11 questions per group, an AI assistant drafted the questions, and the 7 unnamed-note traps reuse the store's only 8 unnamed notes.
